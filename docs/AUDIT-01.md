# 全项目重新验证（AUDIT-01）

> 从项目初始逻辑重新走一遍，不看测试名，只看**每一环的输入输出是否闭合**。
> 结论：**核心不变量全部实测成立；但有 3 处语义缺口会让读者高估系统能力，4 处文档漂移会让新人误解项目阶段。**

---

## 一、方法

```
1  依赖方向：谁 import 谁（静态解析 AST，不靠文档）
2  身份链：同进程 / 跨进程 / 删内核 / 换装载格式
3  不可变：改证据 1 字节 / 删 blob / 改 blob 清单
4  增量：逐条追加，每步与全量比对
5  文档：声明的数字与仓库实际数字逐条核对
```

---

## 二、实测通过的部分

### 2.1 包依赖（AST 解析，非文档）

```
aiinvite/         -> ∅
aiinvite.cn          -> ∅
aiinvite.recall      -> aiinvite, aiinvite/cn
aiinvite.kernel      -> aiinvite, aiinvite/cn, aiinvite.recall
aiinvite.pcs         -> ∅
aiinvite.projection  -> aiinvite
```

**无层级倒置，无循环依赖。** 投影层只依赖证据层（用其 canonical 序列化），不依赖内核实现——
这与「投影只读内核对象」的意图一致。

### 2.2 身份链的四项

| 检查 | 结果 |
|---|---|
| 同进程编译 kid | `b6f79d970bf11ebaa731…` |
| **跨进程**（`PYTHONHASHSEED` = 0 / 12345） | **完全相同** |
| 删掉 `store/kernel/` 重建 | kid 不变 |
| v1 / v2 两种装载（M10 复核） | kid 不变 |

### 2.3 不可变性

| 攻击 | 结果 |
|---|---|
| 改证据 1 字节 | `E_TAMPER: 事件 ev_000001 内容与 hash 不符` |
| 删 blob | `E_BLOB_MISSING` |
| 删 blob **并从 `chain.blobs` 移除** | `E_CHAIN_MISSING: chain.json 与证据不符` |
| 伪造快照 kid（且重算 digest） | 增量时重算比对 → `E_KN_DRIFT` |

**最后一条尤其重要**：`_kernel_from_snapshot` 不用快照里的 kid，而是从产物重算再比对。
所以「伪造快照身份」这条路是堵死的。

### 2.4 增量

逐条追加 6 种事件，每步增量与全量比对：**kid / canon_md / self_md / state 全部逐字节相同**；
计数器 `[1,1,1,1,1,1]`，工作量严格等于增量条数。

## 三、发现的问题

### P1-A1 编译不校验哈希链（最重要的语义缺口）

`read_evidence()` 只解析 JSON 行，**不验证哈希**。

```
后果：谁改了 evidence/seg-*.jsonl，compile 会安静地产出另一个 kid，不报错。
检测依赖：显式跑 python -m aiinvite.cli verify / aiinvite kernel reconcile，或与已知 kid 比对。
```

**这意味着论文里「改 1 字节即被发现」应改为「改 1 字节即**可**被发现（由 verify 命令）」**——
被动检测与主动校验是两件事，不能让读者以为编译会自己报警。

### P1-A2 行为身份与证据层脱钩

```
PCS 的输入：回复文本文件（pcs_out/*.jsonl）
PCS 不读：store 里的证据
```

`aiinvite.pcs -> ∅`（零依赖）在工程上是优点，但它意味着：
**「这个人的行为符合度」无法仅凭证据复算。**
传给别人一个胶囊，他能验证人格（kid），但无法独立验证行为（PCS）——
因为 PCS 需要那份回复集，而回复集不在胶囊里。

这是真实的能力边界，与地基文档 C4「行为 = 对声明规则的符合度」并不矛盾，
但**必须写清楚：行为身份是评测结果，不是可携带的证据**。

### P1-A3 动作不入证据

投影是纯函数（I1/I3 要求），因此**「它做过什么动作」没有任何记录**。
具身形态下这等于没有审计线——`refusal` 事件与动作留痕要等 M13。

`FOUNDATION-INVARIANCE.md` §3 已经写了要加 A 层，但文档没标注「当前未实现」。

### P2-A4 冻结棘轮的真实边界

`ALLOWED_CHANGES` 能保证：**改了文件但没声明 → 测试失败**。
它不能保证：**声明了并且同时改基线 → 通过**。

```
棘轮防的是「偷偷改」，不防「公开改」——后者必须由人审。
建议：基线锚定到上一个 release tag，而不是测试文件里的字典。
```

### P2-B1 `AGENTS.md` 停在 M7（最严重的文档漂移）

```
文档写：当前阶段 M7，已封版到 v0.8-m6，共 193 个测试
实际：  当前阶段 M12，已封版到 v0.15-m12，共 270 个测试
```

而且其中「不可改」表列着 `aiinvite/`、`aiinvite.kernel/` 全部——M10/M11/M12 已经改过它们。
**新贡献者照着这份文档工作，会立刻违规。**

### P2-B2 README 里有三个不同的测试数

```
README.md:7     246 个测试
README.md:26    240 tests
README-en.md:24 255 tests
实际             270
```

同一份文档自相矛盾，这是最容易被外部读者抓到的。

### P3-B3 「胶囊 4 个文件」在 v2 下不成立

演示文档与论文大纲写「胶囊 4 个文件，不含人格」——那是 v1 的事实。
v2 加了 `blobs/`，「4 个文件」不再成立。需要标注版本。

### P3-B4 论文数字缺时间标注

论文写「246 个测试、12 个里程碑」是写作时的事实，不是现在的事实（270 / 17）。
需加「截至本稿」或在附录注明版本。

## 四、逻辑链自查（每一环是否闭合）

| 环节 | 输入 | 输出 | 是否闭合 |
|---|---|---|---|
| 记录 | 对话 | 证据事件 | ✅ 五类事件 + schema 拒绝非法组合 |
| 装载 | 文本/音频/动作 | blob + 摘要 | ✅ 内容寻址、缺失与篡改可检 |
| 派生 | 证据 + 策略 | kid | ✅ 跨进程/跨装载/删内核均稳定 |
| 增量 | 快照 + 新增 | kid' | ✅ 与全量等价，且 kid 重算不信任快照 |
| 投影 | 内核 | 轨迹 | ✅ 两形态、确定性、身份不变 |
| 测量 | 回复集 | PCS | ⚠️ 与证据脱钩（P1-A2） |
| 动作 | 轨迹 | 真实行为 | ⚠️ 未实现、无留痕（P1-A3） |

**七个环节里，前五个闭合，后两个是已知未完成项——不是漏洞，而是里程碑缺口。**

## 五、结论

```
身份与证据层：没有发现漏洞（六类攻击全部被拒）
派生与增量：等价性成立，且不信任缓存
投影：不变量成立
语义层面：3 处会让读者高估（编译不验链 / PCS 不可携带 / 动作无留痕）
文档层面：4 处漂移，其中 AGENTS.md 停在 M7 最严重
```

**建议顺序**：先修 B1/B2（文档可信度）→ 再补 A1/A2/A3 的措辞与标注（诚实性）→ 最后再进 M13。

## 八、P1-A1 从「改文档」升级为「改代码」（2026-11-01，M12.1）

用户质疑得对：这条只改文档不行。补做如下。

### 8.1 先测成本，再决定

```
2000 条事件：
  compile_kernel  596.0 ms
  verify_path      30.4 ms
  verify / compile = 0.05x
```

**校验只占编译的 5%** ——我之前在论文里写「为了速度不验链」是**未实测的假设**，
这是本次审计里第二处「凭印象下结论」。

### 8.2 第一版尝试：默认在库里验（失败）

把 `compile_kernel(verify=True)` 设为默认后：**32 个测试失败**。

```
根因：约 30 个内核测试用手写 fixture 造证据（哈希是假的），
     验链先行 ⇒ 它们在测解析之前就被拒绝了。
更关键：这暴露了分层错了——「是否信任输入」是**边界决定**，不是纯函数该管的事。
```

### 8.3 最终设计：库信任输入，CLI 默认校验

```
compile_kernel(..., verify: bool = False)   库：纯派生，信任调用者
aiinvite kernel compile                          默认 verify=True，篡改即 E_KN_TAMPER
aiinvite kernel compile --no-verify              显式快路径
把一条被禁的快路径写出来，比藏着不给要好
```

### 8.4 实测

| 场景 | 结果 |
|---|---|
| 干净 store 编译 | 正常，kid 稳定 |
| **篡改 1 字节后 `aiinvite kernel compile`** | **`E_KN_TAMPER: 证据未通过校验：E_TAMPER…`** |
| `--no-verify` | 编译成功（显式选择） |
| `verify=True` 的底层异常 | 保留 `__cause__`，可追到 `AiInviteError` |

新增测试 4 个（`tests/test_compile_verify.py`），全量 **274 全绿**。

### 8.5 顺带发现的第三个问题

`tests/kn_fixtures.py` 造的证据**不是链合法的**（directive 缺 `kind`）：
编译器宽容、校验器严格，两者标准不一致。

```
处置：本轮不改 fixture（会改动多个里程碑的 kid 断言），
     在 test_kn_history 的 CLI 用例上显式走 --no-verify 并写明原因。
记录：fixture 与真实写入器的 schema 差异，属测试基础设施债务。
```

### 8.6 结论修正

```
原文：改 1 字节即可被发现（需显式 verify）
现在：改 1 字节即被发现——CLI 编译默认先验链
论文 §4.2 的注也已同步改写（不再声称「为了速度」）
```
