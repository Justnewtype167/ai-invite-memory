## 2. R6 的问题：它过了，但过法是抛硬币

我在 1000 / 10000 / 50000 / 200000 四种规模下各测 15–60 次：

```
n=1000     p50 24.2ms   p95 41.2ms
n=10000    p50 48.8ms   p95 60.8ms
n=50000    p50 28.3ms   p95 36.3ms
n=200000   p50 60.9ms   p95 79.5ms   ← 门禁 80
```

两个结论：

1. **延迟不随规模增长**（50k 比 10k 还快）——这是好消息，说明算法是次线性的
2. **方差极大**（同一实现，p50 在 24–61ms 之间跳）——说明瓶颈是固定开销与调度噪声，不是索引大小

所以 `p95 < 80ms` 这条门禁：**这次 79.5 过，下次大概率 85 红。**

这跟 M2 的 T7 是同一个错误——**把 SLO 写成了单次硬门禁**。当时的结论是「真实 SLO 交给 bench，单测只防回归」，
这次我没吸取，是我的疏漏。

### 改法（规格已在 v0.2 修订）

```
单测断言（稳定）：
  p95 < 200ms                                    ← 防算法退化
  p50(200k) <= 2 × p50(10k)                      ← 防随规模劣化（这才是真属性）
报数（不进单测）：tools/bench_recall.py 输出 p50/p95/max，目标 80ms
```

## 3. 加测的一项：预算压力

官方 R7 只用了 204 token（远未触及 4096），说明它没测到**预算压力**。我另外造了一个：

```
500 条都含「手术」的干扰 + 1 条金句「我妈下周三做手术」
query：我妈手术是什么时候
结果：预算 4096 → 用了 1134，60 条 item，**金句仍在**
      预算 600  → 用了 545，未超
```

**通过了。** 说明排序不是只靠词频，实体差异起了作用。这一条建议固化进 R7。
